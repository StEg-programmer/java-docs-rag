# Инструкции AI-агентам

## Назначение и границы

Java Documentation RAG System — университетская лабораторная работа на Python 3.11.
Используется src-layout: `src/java_docs_rag`. Сейчас репозиторий содержит только
контракты и заглушки. Реализовывать функциональность нужно отдельными задачами.
Перед работой изучайте существующие файлы, `git status` и документацию.
Сохраняйте изменения пользователя и другого разработчика.

## Архитектура

- Индексация: grabber → preprocessing/chunking → embeddings → vectorstore.
- Ответ: retrieval → reranking → filtering → generation.
- `pipeline` связывает этапы, `common` определяет общие модели и Protocol.
- `evaluation` измеряет качество, `observability` отвечает за трассировку.
- Направляйте зависимости на `common.interfaces`, передавайте адаптеры явно.
  Импорты и конструкторы не должны выполнять сеть, скачивание или запуск моделей.

| retrieval, reranking, filtering, generation, evaluation | Developer A (Codex) |

Не изменяйте чужие модули без предварительного согласования с их владельцем.
Изменения общих контрактов согласуйте с обоими разработчиками; документируйте
миграцию потребителей. Изменение тестов следует владельцу соответствующего модуля.
Разрешение на создание исходного каркаса охватывает все области; дальнейшие
задачи должны соблюдать указанные границы. Универсальное разрешение на текущую
задачу не означает разрешение на будущие изменения чужого кода.

## Контракты и стиль

- Python `>=3.11,<3.12`, type hints для публичных функций, Ruff.
- Модели — frozen dataclass; вложенные list/dict остаются изменяемыми.
  Передавайте их как значения, не мутируйте данные другого этапа.
- `metadata` содержит только строковые ключи и значения.
- Контракты синхронные; векторы — `list[float]`, batch сохраняет порядок текстов.
- Детали будущих ID, хеширования, порогов и метрик фиксируйте в `docs/decisions`.
- Заглушки явно поднимают `NotImplementedError`, а не возвращают фиктивные ответы.
- Никаких секретов, платных API и сетевых вызовов в unit-тестах.
- Не устанавливайте torch, sentence-transformers и модели без отдельной задачи.
  Docker и загрузку моделей запускайте только по явному указанию пользователя.

## Тестирование

После согласованных изменений выполните из корня:

```powershell
.\.venv\Scripts\python.exe -m pytest
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe -m ruff format --check .
```

Используйте исключительно проектную `.venv` для локальных проверок и установки
зависимостей; системный Python 3.10 не использовать. В CI применяется Python 3.11.
Unit-тесты должны работать без внешних сервисов. Будущие integration-тесты
помечайте `@pytest.mark.integration` и пропускайте, если сервис явно не включён.
Не маскируйте ошибки сервисов как успешные проверки. Добавляйте тесты поведения
при реализации функций; не закрепляйте устройство заглушек тестами.

## Git

- Работайте небольшими изменениями в ветках `feature/a-...` и `feature/b-...`.
- Перед работой и перед сдачей проверяйте `git status` и diff.
- Не выполняйте commit, push, merge, rebase, reset и удаление чужих файлов без
  явного поручения. Не добавляйте секреты, модели, данные и состояние Qdrant.
- Описывайте изменённое поведение, проверки и ограничения в PR/отчёте.
- Файлы изменяйте только внутри проекта. Не переписывайте историю Git.
